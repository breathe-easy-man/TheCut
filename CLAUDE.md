# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project Goal

**theCut** — a Capacitor-based Android app wrapping a single-page calorie/protein tracker.
Grew out of a standalone `Daily Tracker` HTML file; the data format is unchanged, so a backup
exported from that page restores into this app as-is.

Four things this adds over the original page: configurable goals derived from bodyweight,
a launch screen with rotating bodybuilder quotes, and a meal-photo estimate that calls Claude
and prefills the Add-meal form.

## Repository Layout

```
www/
  index.html          ← markup only
  styles.css          ← every colour is a token; see Theme
  app.js              ← UI logic and Capacitor glue
  fonts/              ← the bundled IBM Plex Sans subset
  tracker-core.js     ← pure logic, shared with the test
test/
  tracker-core.test.mjs
capacitor.config.json
android/              ← generated by `npx cap add android`
```

`tracker-core.js` exists because inline script cannot be imported by a test. Everything pure —
targets, step maths, the meal request and its response parsing — lives there; `app.js` keeps
the DOM. Run `npm test` (plain `node`, no framework, exits non-zero on failure).

`android/` is generated. Do not hand-edit it except `AndroidManifest.xml`, which carries the
camera and media permissions `cap sync` does not add.

## Goals and the history snapshot

Targets derive from bodyweight, which by default follows the most recently logged weight.
Defaults are calibrated so day one reproduces the original hardcoded numbers: at 99.7 kg,
29.59 cal/kg = 2950 maintenance and 1.91 g/kg = 190 g protein, rest day −400, training +200.

**A day marked finished stores the maintenance and protein figures it was scored against**
(`day.maintenance`, `day.proteinTarget`). Without that snapshot, losing weight lowers current
maintenance and retroactively shrinks the deficit on every past day, so the fat-loss bar runs
backwards while the cut is working. Unfinished days deliberately float with current settings so
that editing a goal previews its effect. `test/tracker-core.test.mjs` pins this behaviour —
if a change makes those assertions fail, the change is wrong, not the test.

**Finishing is automatic.** `finalizeDays()` runs at launch and on resume: every day strictly in
the past holding at least one meal is marked `done` and snapshotted. There is no manual toggle —
`shouldFinalize()` is the whole rule. A past day with no meals is *skipped*, never scored as a
full day of deficit, because scoring it would invent a day's worth of deficit for a weekend away.
The snapshot uses `weightAsOf(days, date)` — the weight logged on or before **that day**, not
today's — so being away four days does not freeze all four against one morning's weigh-in. When no
weight was ever logged by then it returns 0, which `bodyweight()`'s falsy check turns into the
settings weight rather than a zero in the history.

Only today can ever be unfinished, so the app cannot show a "mark this finished" affordance and
should not grow one back.

## The training week and the muscle split

Two features that are **derived, never stored**, which is what keeps the backup blob
byte-compatible with the original standalone tracker. Safe to derive only because a label feeds no
arithmetic — unlike `maintenance`/`proteinTarget`, recomputing one cannot corrupt a past day's
deficit.

`MUSCLE_GROUPS` + `workoutSplit(days, date)` roll four groups forward **one slot per training day
that has something logged on it**, not per calendar day. A day you skip postpones its group rather
than skipping it. The "something logged" condition is what keeps that true once a schedule is set:
without it, a scheduled day you never trained would still burn a slot and the rotation would
degrade into the date-anchored cycle the per-workout design exists to avoid. It counts *strictly
earlier* days, so marking today done never renames today's own tile.

`settings.trainingDays` + `isTrainingDay(settings, dateStr)` hold the weekly schedule as a string
of `Date#getDay` indices (`"1,2,4,5"`), **not an array** — `withDefaults()` copies by reference and
one shared mutable default array would be edited in place by every caller. Empty is the default and
means the pre-schedule behaviour exactly: every new day opens as rest.

`defaultDay(date)` stamps the schedule on **today and later only**. `getDay()` materialises a day
merely by reading it, so browsing back through the day strip would otherwise invent workouts that
never happened, moving those days' calorie targets and the rotation that counts them. Changing the
schedule re-stamps today only while it is still untouched (`isEmptyDay && !done`) — after that the
user owns the day.

## Meal photo → Claude

`www/tracker-core.js` builds the request; `app.js` takes the photo and posts it.

- Camera via `@capacitor/camera`, `resultType: 'base64'`, `width: 1024`, `quality: 60` — the
  resize happens on-device and keeps the call around **$0.006 per photo**.
- `CapacitorHttp` is enabled in `capacitor.config.json`, which routes `fetch` through native
  Android. That is what makes a direct call to `api.anthropic.com` work at all — the WebView
  would otherwise fail CORS. Do not "fix" a CORS error by adding a proxy before checking that
  flag is still on.
- Model `claude-opus-5` with `output_config.format` (`json_schema`), so the reply is always one
  text block of valid JSON. `effort: 'low'` — this is an extraction, not a reasoning task.
- `parseMealResponse()` trusts nothing: API errors, refusals and truncation all arrive as an
  ordinary HTTP 200 object. On any failure the form is left empty and the user types it in.

The API key lives in `settings.apiKey` in `localStorage`, entered on the Settings tab. It is
**excluded from the backup blob** (`exportable()`) because that text gets pasted around, and it
is never logged. Keep both properties.

## Home-Screen Widget

Three bars — fat loss against the goal, calories and protein against today's targets — over a
button that opens the app straight into the camera.

| File | Role |
|---|---|
| `android/.../CutWidget.java` | `AppWidgetProvider` — renders the blob, owns the two PendingIntents |
| `android/.../WidgetBridge.java` | Capacitor plugin — the only door between WebView and widget |
| `android/.../res/layout/cut_widget.xml` | three static rows (RemoteViews needs static ids) |
| `android/.../res/drawable/w_bar_*.xml` | one layer-list per bar; the fill colour is what differs |
| `android/.../res/values{,-night}/colors_widget.xml` | the two themes |
| `www/tracker-core.js` | `widgetBlob()` / `fatLost()` / `pct()` |

**Why a bridge exists:** the widget runs in the launcher's process and cannot read WebView
`localStorage`. `index.html` pushes an already-computed blob into `SharedPreferences` (file
`cut_widget`, key `state`) and the widget only renders it. Every number is worked out in JS where
it is already under test; the Java side stays dumb.

```json
{ "date": "YYYY-MM-DD",
  "bars": [ { "label": "FAT LOST", "value": "1.24 / 3 kg", "pct": 41, "over": false }, … ] }
```

Unlike psych_app's widget this one is **read-only** — it displays and launches, it never writes
state back. So there is no merge, no signed timestamps, no pull-before-push. Keep it that way: a
widget that can only launch the app needs none of that machinery.

`syncWidget()` hangs off `save()` rather than each call site — every mutation in the app routes
through that one writer, so the widget cannot drift.

**Light and dark come free.** Every colour in the layout is a resource, and the launcher inflates
`cut_widget.xml` in its own process under the current `uiMode`, so `values-night/` is picked up
with no code and no state. The one exception is the over-target colour on the calorie figure,
which Java resolves with `ContextCompat.getColor` against the *app's* resources — correct only
because the app never overrides `uiMode`. If the app ever gains a manual theme switch, that line
has to move into the layout (two stacked `TextView`s) or it will disagree with the launcher.

**Bars are `ProgressBar` + `setProgressBar()`, not bitmaps.** A layer-list with
`@android:id/background` and a clipped `@android:id/progress` is what `RemoteViews.setProgressBar()`
drives, and because each fill is a colour resource the night variant swaps itself. Going over the
calorie target caps the bar at 100% and turns the figure red rather than overflowing.

**The two taps are distinct PendingIntents with different request codes** (0 = open the app,
1 = open the camera). `PendingIntent` equality ignores extras, so sharing a request code would
make the second registration silently rewrite the first and both taps would do the same thing.

**The camera extra is consumed once.** `MainActivity` is `singleTask`, so the launching Intent
stays attached across resumes; `consumeAction()` removes the extra as it hands it over, and
`onNewIntent` swaps the stored Intent so a tap on an already-running app is still seen. Without
either half the camera would re-open on every resume, or never open at all.

**`minResize*` is what makes the launcher offer resize handles.** Left out it defaults to
`minWidth`/`minHeight` and One UI shows no handles. Metadata changes reach **new** widgets only —
remove and re-add the widget to see them.

## Theme

The app follows the system light/dark setting through CSS custom properties: one `:root` block of
tokens and one `@media (prefers-color-scheme: dark)` block that redefines them. Nothing else in
the stylesheet knows which theme is running, so a new colour belongs in the token list, not inline.
`color-scheme: light dark` on `:root` is load-bearing — without it the native date picker and
number spinners stay white boxes on a dark card. The launch screen is deliberately dark in both
themes; it is a title card, not a surface.

## Automatic Step Counting

`TYPE_STEP_COUNTER` — the low-power counter in the phone's own sensor hub. Deliberately **not**
Samsung Health (partner SDK, Samsung-only, would strand every other phone), **not** Google Fit
(APIs being retired) and **not** Health Connect (depends on some other health app actually
writing steps on each device). The raw sensor is present on every modern Android phone and behaves
identically on a Samsung and a POCO with no account, no companion app and no Play dependency.

| File | Role |
|---|---|
| `android/.../StepCounter.java` | Capacitor plugin — `check` / `request` / `read` |
| `www/tracker-core.js` | `stepTally()` — cumulative reading → steps today |

**The sensor reports steps since boot, not steps today.** `stepTally()` turns one into the other by
keeping `{ day, base, carried, last }`: a day's total is the delta against the first reading taken
that day. Its tests are the specification — read them before changing it.

**A reboot zeroes the hardware counter**, which shows up as a reading *lower* than the last one.
Steps counted before the reboot are banked into `carried` and a fresh baseline starts. Without
that branch a reboot at lunchtime either wipes the morning or yields a negative delta.

**The permission is requested lazily.** `ACTIVITY_RECOGNITION` only exists from API 29 (below that
the sensor is readable outright), and `autoSteps` defaults off, so nothing is asked for at first
launch — flipping the Settings switch is what prompts. `uses-feature ... required="false"` keeps
the app installable on a phone with no step sensor; `check`/`read` then report `available: false`
and the UI says steps stay manual.

**Reads happen on launch, on resume, and every 10s while the app is visible** — the poll stops the
moment the app is backgrounded, so there is still no background service and the app costs no
battery of its own; the sensor hub counts regardless. A read only writes and re-renders when the
figure actually changed, or the repaint would wipe whatever the user is part-way through typing. **Known ceiling:** steps are attributed to the day
they are *read*. Go two days without opening the app and the second day's reading only claims what
accrued since the app last looked. Opening the app once a day — which logging meals already
requires — keeps it honest. Fixing this properly means Health Connect or a scheduled worker;
neither is worth it until the gap actually bites.

**Typing in the Steps field wins for that day** (`day.stepsManual`), and clearing it hands the day
back to the sensor. The baseline advances even on a hand-typed day, so resuming automatic counting
picks up from the right place instead of claiming every step since boot.
